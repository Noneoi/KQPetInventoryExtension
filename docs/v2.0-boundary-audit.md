# v2.0 六个构建边界审计与拆分清单

审计日期：2026-09-12。依据当前工作区 `CMakeLists.txt`、`src/extension`、`src/application`、`src/storage`，以及重构计划第 4 节。工作区仍有并行改动；以下行号是本次读取的定位线索，实际符号比行号更稳定。本文件只记录已读取的依赖和建议，不表示边界拆分已经完成。

## 1. 当前结论

当前 `KQPetCore` 不能改名后直接称为 Domain。它同时编译纯计算、可变 Repository、控制器、存储用例、读取资源的 Catalog 单例，以及 HTML Renderer。其 PUBLIC 链接包含 Diagnostics、Protocol、Storage、ReadViews、Transport；`KQPetUi` 还 PUBLIC 链接整个 Application。现有分线程工作是必要基础，但尚未形成计划要求的六个依赖边界。

最短的正确路径是先拆混合翻译单元与公共类型，再调整 CMake。尤其不能把 `asset_analyzer.cpp`、`recommendation_engine.cpp` 或 `pet_detail_catalog.cpp` 整体移入 Domain：它们确有纯函数，也确有运行时对象、单例和资源读取依赖。

## 4. 必须先拆的混合翻译单元

### 4.1 AssetAnalyzer 与 Recommendation 的反向依赖

证据：

- `asset_analyzer.h:10` 构造函数接收 `PetRepository*`、`ShopExchangeController*`、`RoutineOverviewController*`。
- `asset_analyzer.cpp:3–13` include 了纯战力函数、协议契约、Recommendation、三个运行时数据/目录对象。
- `captureInput():174` 从 Repository 读取账号/epoch/revision、详情、元数据，并从控制器采集已知性。
- `analyzeRoutine():52` 从 RoutineController 和 `RoutineOverviewCatalog::instance()` 读当前信息。
- 同一 cpp 的 `identityFields():159`、`derivePet():228`、`accumulate():273`、`matchesFilter():330` 是可以使用值输入的纯算法。
- `recommendation_engine.cpp:148/208/210/224` 调用 `AssetAnalyzer::identityFields/accumulate/derivePet`。若只把 Recommendation 移到 Domain，它仍需链接整个 AssetAnalyzer 所在的应用对象文件。
- `asset_analysis_filter_proxy_model.cpp:29` 仅为 `matchesFilter` include `asset_analyzer.h`，把 UI 与包含 Repository 构造函数的类型耦合。

执行拆分：

1. 新建 Domain `asset_derivation.h/.cpp`，迁移 `identityFields`、`derivePet`、`accumulate`、`matchesFilter` 及其纯辅助函数 `hasGap`。命名可调整，但公开签名只能有值/不可变元数据，不能声明 Repository/Controller。
2. RecommendationSession 改调这些 Domain 函数，AssetAnalysisFilterProxyModel 改 include 纯过滤接口。
3. 现 `asset_analyzer.*` 的 Repository 捕获、controller/routine 汇总及同步兼容入口留在 Application，或者改名为明确的输入采集适配器。`analyze()` 中 while(step) 的同步测试入口不能成为 GUI 的计算入口。
4. `analyzeRoutine` 可后续拆成 `RoutineObservation + RoutineCatalogSnapshot → summary` 的纯函数；读取控制器、确定是否可信、绑定当前会话仍由 Application 承担。

### 4.2 RecommendationEngine 的旧入口

`recommendation_engine.cpp:93–116` 的 `RecommendationEngine::generate` 遍历成本，从 `PetDetailCatalog::instance().materialName()` 取名称，再取 `stargodDefinitions()`。同文件的 `RecommendationSession`、`generatePrepared`、排序 `less` 与 `applyFreshness` 已经接受冻结输入，可组成真正 Domain。

可执行方案：让 Domain 的 `generate` 显式接收 material names/definitions 与 `ShopPetMetadataSnapshot`；或把旧入口移为 Application 的 `RecommendationAdapter::generate`。不要在 Domain 公共头继续声明一个只有链接 Application 才能得到实现的“旧 overload”，也不要给新元数据参数提供读取单例的默认值。

### 4.4 Catalog 类型、解析、持有与读取

三个 Catalog 头同时声明了值与单例，必须先提取头：

- `shop_exchange_catalog.h`：`ShopExchangeGood`、`ShopExchangeShop`、`ShopCatalogSnapshot` 移入 Domain `shop_catalog_types.h`。`isOnlineOn(date)`、`itemKey()`、`stableKey()` 的纯实现移 Domain cpp。`shops/onlineGoods` 改为在传入 snapshot 上操作，日期由调用者冻结；不要保留 `QDate::currentDate()` 作为领域计算的隐式时间。
- `routine_overview_catalog.h`：`RoutineTaskDefinition`、`ActivityOverviewDefinition`、`RoutineCatalogSnapshot` 移 Domain 值类型头。
- `pet_detail_catalog.h`：`PetDetailCatalogSnapshot` 与只读查询/索引的值接口移 Domain。`sacredMaxStar/sacredMaxStage` 可直接成为纯规则函数。元数据查询接收同一个 snapshot，避免一个分析内多次重新读取全局 snapshot。

不能直接移动现有 Catalog cpp 的证据：

- `pet_detail_catalog.cpp:55–56` 构造函数 `QFile(":/kqpet/pet-detail-data.json")`；`shop_exchange_catalog.cpp:80` 同样读取 RCC 资源。即使 RCC 是内存资源，这仍依赖运行时资源注册与单例初始化，不是显式值输入。
- 三个 `instance()` 都返回进程全局持有器。当前快照原子发布解决了读写撕裂，但没有消除 Domain 对运行时当前状态的依赖。
- `shop_exchange_catalog.cpp:289`、`routine_overview_catalog.cpp:361` 的官方文本解析生成当前 UTC 时间。若作为纯解析函数，应把该时间作为参数；或留给 Storage 导入适配器补来源时间。
- `catalog_io_service.cpp:2–5` 依赖三个 Catalog 和 Transport；`publish()` 调用 Catalog 的私有发布入口。它当前是 Core 用例 + IO 工作流，不可整体加入底层 Storage 后反向链接整个 Application。

建议最终分工：Domain 持有值结构、纯验证/索引/查询；Storage 的 catalog reader/parser 从资源/路径/文本读入并返回不可变候选值；Application 持有当前快照、账号/请求 generation 和发布决定。先保留现 Catalog 类在 Application 作为过渡，但 Domain/UI 只接收冻结快照。若把完整纯 `prepare(root,source,time)` 放入 Domain，去除 `instance/QFile/currentDateTime`，并保持坏候选整份拒绝的语义。

### 4.5 数字契约与 Protocol 依赖

`pet_power_calculator.cpp:2/11` 因 `checkedInteger` include `packet_contract.h`；纯 Asset 派生/累计也调用 `PacketContracts::checkedInteger/checkedAdd`。后者头第 3 行 include `session_context.h`，并声明发送白名单、关联强度等 Application 协议概念。

提取 Domain `checked_json_numbers.h/.cpp`：保留有符号范围、字符串精确整数、JSON 数字最多 2^53−1、checked add/multiply 的现有语义。PacketContracts 调用或薄封装这份实现，使 Protocol → Domain，而不是 Domain → Protocol。不能只在 Domain 链接整个 `KQPetProtocol`，更不能复制一份宽松解析破坏现有协议边界。

### 4.6 战力类型与详情展示

- `pet_power_calculator.h:2` 当前 include `pet_detail_view_model.h`；该头前部是 `PetBattlePowerState/Gap`，后部却含 `PetDetailViewModel.imagePath/fetchingLatest`、展示名称和关系行。
- 将纯 `PetBattlePowerState/Gap` 提到 Domain `pet_power_types.h`，Domain `pet_power_calculator.*` 只依赖它和数值契约。UI 的详情 ViewModel 再 include 该值头。
- `pet_detail_analyzer.cpp:74` 通过 `InventoryReadView::detailFor()` 寻找关系个体；`analyzeBattlePower():122` 读取 Catalog 单例；`analyze():127` 同时解析培养与格式化文案。它目前是混合的详情投影构建器，不应整体加入 Domain。
- 最终以选中详情值、所需关系记录值、冻结元数据构建详情展示结果。账号/选中项匹配和关系查询在 Application；纯战力调用 Domain；图片路径、HTML、展示文案在 UI。可以保留一个共享详情 builder，不要求把每个 JSON 字段机械建类。
- `pet_detail_renderer.cpp:120–147/382–456` 拼接 CSS class/HTML；`:504` 的便捷 overload 又调用 PetDetailAnalyzer。它应移 `src/ui`，即使只链接 QtCore 也不属于 Domain。纯 `render(PetDetailViewModel, options)` 可保留；抓取/分析便捷 overload 应移编排层或改为输入完整 ViewModel。

### 4.7 搜索的平台适配

`pet_search.cpp:10/44` include Windows 并调用 `WideCharToMultiByte(936,...)` 生成拼音首字母；查询匹配函数本身是纯值计算。QtCore-only 的 Domain 不应暗藏 Win32 字符集转换。

建议保留 `PetSearchText/Index/Query` 与已准备索引上的匹配算法在 Domain；把 GBK 首字母生成移 Application/Compute 的 `pet_search_index_builder` 适配器，发布预生成的索引给 UI。另一可行方案是经过现有中文/修正用例验证的固定首字母表。不能换一种转码后悄悄改变搜索结果，也不能把平台函数挪到 Compatibility（它与宿主兼容核验无关）。

### 4.8 MoveOutcome 与 Journal

`move_operation.h` 把 `SubmissionOutcome/MoveOutcome`、`moveOutcomeName` 与 `MoveOperationJournal` 放在一起；Journal 带 `QPointer<StorageService>`、冻结 StorageContext、提交与恢复记录。`runtime_types.h:3` 和 Transport 因枚举包含了整个 Journal 头。

将 outcome 值及纯名称映射移 Domain 或轻量 Application contract 头；Journal 保留 Application 的持久化用例适配器。Storage 提供原子写队列，不掌握当前移动状态机。之后 Runtime/Transport/UI 不再通过 outcome 引入 journal/storage 实现头。

## 7. 推荐构建关系和实施顺序

最终依赖（箭头表示“依赖”）：

```text
Domain                 → Qt6::Core
Application contracts  → Domain + Qt6::Core
Protocol / Transport   → Domain + Application contracts（无 UI）
Storage                → Domain 值/codec（需要时）+ Qt6::Core + 明确的 OS IO 库
Application            → Domain + contracts + Protocol/Transport + Storage
Bridge                 → Compatibility + Protocol/Transport contracts + 宿主 Qt/MinHook
UI                     → Domain 展示值 + Application contracts + Qt6::Gui/Widgets
DLL composition        → Compatibility/Startup + Bridge + Application + UI
```

contracts、AnalysisWorker、Catalog IO、Images 可以是主边界内有实际职责的子库；不要求整个工程恰好只有六个 add_library。图片 IO/解码的 QtNetwork/QtGui 依赖留在对应适配子库，禁止传进 Domain；Domain 不创建线程。UI 不 PUBLIC 链接整个 Application 实现来取得一个 DTO。

建议按下列顺序落地，每步有可链接的产物：

1. 提取 shop/routine/pet metadata 类型、power 类型、严格数值函数、outcome/timings 类型，改 include，不改变业务结果。
2. 提取 asset_derivation；切开 Recommendation/eligibility/actionability 的 legacy adapter；建立只链接 QtCore 的 Domain，并把真正纯对象加入。
3. 将 Repository/Controller、分析捕获、快照/设置/Journal 用例从 Core 移 Application。AnalysisWorker 改链接 Domain；Application 链接 Worker，不形成相互依赖。
4. 将 Renderer/展示 builder 移 UI；UI 的目录、搜索索引、战力、资格来源改为冻结 DTO/端口。去掉 Ui → Core/App implementation 的全量 PUBLIC 依赖。
5. 拆 Catalog 文件/资源 reader、纯验证、当前快照持有者；接现有 CatalogIoService 时核对 IO 工作与 Core 发布所在函数，不把整个服务硬塞 Storage。
6. 物理整理 `src/domain`、`src/application`、`src/storage`、`src/ui`、`src/bridge`，收窄 PUBLIC include 目录。当前源都在 `src/extension` 时，即使不设置该 PUBLIC include，编译器仍会从同目录找到私有 Controller 头，因此只有链接库名单不能阻止误依赖。
7. 最后删除混合 Core 静态库；若为已有脚本暂留 `KQPetCore` 名字，只可作过渡聚合别名，不能把它当作 Domain 证据。测试改链接其真正测试的边界。

## 8. 证明边界完成所需的验证

- Domain 目标实际只声明 QtCore，并单独构建一个无 qrc、无 Repository、无 Controller、无 Storage/Bridge 的算法测试程序。覆盖真实纯流水线与极值/未知值/排序语义。
- 静态库链接可能隐藏“未被引用的坏对象”；使用 MSVC `/WHOLEARCHIVE` 对 Domain 做专门链接检查，或显式逐个调用全部公开实现，保证没有 Catalog/Storage/GUI/协议白名单的未解析符号被最终大程序悄悄补齐。
- 对 include 和 target 归属建立检查：Domain 禁止 include Application、Storage、Bridge、UI 的实现头；禁止 QWidget/QPixmap/QNetwork/QFile/QDir/QSettings/Win32 适配 API、`Catalog::instance()` 与隐式当前账号读取。不能仅搜索 `QWidget`，因为 QtCore 本身也含文件 API。
- 领域时间/元数据作为输入：同一冻结输入在运行时目录发布、切账号、日期变化后仍得到相同结果。Domain 测试不依赖进程先前构造某个单例或注册 RCC。
- 原 recommendation/algorithm/power/snapshot 有效断言继续保留。纯算法计数与候选复杂度用 Domain 测试；Repository/迟到响应/日志/IO/会话测试链接 Application/Storage；图片与 UI 测试链接各自适配目标。
- GUI 线程监测确认窗口动作没有退回全量培养计算或目录读取；仅仅 Domain 抽出来后由 GUI 同步调用，不能满足线程与响应预算。
- 显式枚举允许的跨边界公开头。测试“Ui 不 include Controller、Domain 不 include运行时Catalog”等规则，比只把 target 改名更能阻止回归。

## 9. 本轮 Runtime/Context 修复复核

读取到的新实现已修复前次报告的四类问题：

- `imageServiceReady` 后有 QPointer 与 closing 再检查，删除 facade 时不会继续 emit Ready；smoke 新增删除槽。
- PersistenceSummary 按记录保留失败，只有同记录且 revision 足够新的 Saved 清除；Superseded 不宣称保存。新测试覆盖旧 Saved/new failure 与失败摘要上限。
- Runtime 以一个 `persistence` 邮箱项合并事件；Storage 完成后重新发布当前会话与全局 pending 数，避免旧账号完成导致新账号 Pending 永久残留。smoke 新增 1,000 条事件突发。
- Context 缓存持久化 DTO，首次打开/会话变更重新应用；list/detail/move 的页与任务栏状态均核对 account/epoch。

上述为源码与测试覆盖复核，不替代 root 的统一构建执行结果。仍有一个文案证据缺口：摘要超过八条时写“更多失败记录见本机诊断”，但本次读取未发现 Runtime 对每条普通 persistence 失败调用结构化日志，而既有控制器日志也不覆盖所有文件失败。应改成不承诺存在明细的说明，或接真实有界诊断事件，并说明日志可能因容量/退出而丢弃。诊断模块本身不保证任何单条事件一定落盘。
