# 设计与逆向依据

本文区分官方字段证据、实现与需要真实客户端确认的行为。核对日期为 2026-09-12，2026-09-19 合并了原《客户端版本自适配》并更新源码路径；本文本身不构成正式发行或真实账号验收通过声明，实际状态以对应产物的随包验收报告为准。操作命令以 [README](../README.md) 为准。

## 1. 承载程序与发布结构

功能承载于原版氪奇 Pro 进程。D:\奥奇工程\逆向\逆向 中的复刻工程和报告仅作研究材料；原版没有本项目可重新编译的源码，因此采用稳定入口、版本加载器和注入式 Qt DLL。

当前加载链：

~~~text
客户端根 KQPetLauncher.exe（Bootstrap）
  → 校验 active/恢复记录及 manifest
  → KQPetRuntime/releases/{releaseId}/KQPetLauncher.exe
  → 检查原版、配对 DLL identity 和运行目录
  → 启动原版 KQPro，加载该版本 KQPetInventory.dll
  → Compatibility → Core/Bridge → 真实工作台入口就绪握手
~~~

DLL 映像被加载不等于工作台已可用。启动通道区分 ImageLoaded、Compatible、BridgeReady、Ready 与 Failed。版本加载器需要 Bootstrap 提供明确的 --client-root；任意 pending 目录或手工拼接的 DLL 不构成加载授权。

KQPro 磁盘文件不打补丁、不重打包、不重新签名。部署暂存的是完整版本目录，运行中不替换激活记录或入口；关闭后重跑部署完成激活。旧配对备份、v2 回退和卸载行为见 README 及 src/runtime、scripts 中的实际实现。

## 2. 兼容与桥接证据

权威机器输入为 profiles/targets.json。CMake 生成 Profile 表，离线 CompatibilityCheck 与 DLL 运行时复用同一兼容核心。不能只依据文件名、签名“看起来相同”或历史 RVA 强行挂钩。

目前目录登记了两个客户端 Profile，三个入口均使用 `UniqueSignature`（在当前可执行段内唯一匹配签名）：

| Profile | Dispatch RVA | ServiceGetter RVA | CommandSender RVA | 备注 |
|---|---:|---:|---:|---|
| kqpro-1.1.3-x64 | 0x115920 | 0x115450 | 0x116470 | 历史接口特征 |
| kqpro-1.1.4-x64 | 0x140270 | 0x13FDA0 | 0x140DC0 | 登记了原版 EXE 摘要，作为证据记录 |

表中 RVA 是登记这两个家族时的位置，只作为接口特征的历史依据；完整签名、Qt 模块及 QCefView 导出以该文件为准。1.1.4 的独立证据在 [兼容性文档](compatibility-v1.1.4-evidence.md)。

### 2.1 客户端版本自适配

客户端文件名、版本资源、整文件 SHA-256 和历史 RVA 不再作为启用条件。运行时从当前 PE 可执行段唯一定位 Dispatch、ServiceGetter、CommandSender。多个家族解析到相同入口时采用更完整的特征，解析到不同入口时拒绝启用。ASLR 后使用实际模块基址，不把 0x140000000 当运行时固定地址。

ServiceGetter 仅忽略已核实的 RIP 相对位移四个字节；指令本身必须匹配，位移指向的完整指针槽必须位于当前映像的可读段内，包括正常的零初始化区。DLL 核验当前进程时仍逐字节比较磁盘与映射的实际入口，包括这四个字节。

启动器和 DLL 使用同一套识别逻辑（`src/compatibility`）。检查包括有界 x64 PE 解析和可执行节范围；Qt 要求 AMD64 / Qt 6、同一客户端目录、各 Qt 模块版本一致，并检查当前扩展实际导入的符号；QCefView 的 JavaScript 接口也必须存在。新客户端版本和新的 Qt 6 次版本可以通过；未识别接口、冲突特征或不兼容 ABI 会显示具体原因并保留原版运行，不按旧地址尝试。

自动发现支持改名的 EXE，并优先选择能够唯一识别接口的客户端；传统文件名仅用于多个候选的优先顺序和原版回退。部署、启动和运行中检测均使用真实完整路径。`verify-target.ps1 -OriginalExe <完整路径> -ExtensionPath <扩展 DLL>` 可离线检查指定文件，不启动客户端。

定向回归使用从零构造、从不执行的 PE：任意文件名、99.42.0 版本资源、新哈希、迁移入口及 Qt 6.9.0 可通过；缺失导出、Qt 7、重复或变异接口、越界位移被拒绝。改名客户端的选择和运行中判断有单独回归。测试通过不表示未来接口发生变化后也可以继续调用旧接口。

Hook 后端使用随源码固定的 MinHook；允许安装的入口仍由已审查 Profile 限定。成熟重定位库不代表所有函数前导或所有版本都获得授权。来源与依赖记录见 third_party/minhook-provenance.json。

历史桥接报告包括：

- D:\奥奇工程\逆向\逆向\reports\bridge-protocol.md

## 3. 官方协议与身份

主要只读入口和移动命令来自官方 ActionScript 的 PetClient、PetDataService、仓库 Controller 及 PetBuild/PetBriefInfo：

| 场景 | Ext | cmd | 参数/关键字段 |
|---|---|---|---|
| 背包 | PJXExtension | 2_1_10 | 参数 {}；pps 顺序、pl 个体、ppc 容量 |
| 仓库 | PJXExtension | 2_1_S | 参数 null；ns、rb、es 分区 |
| 单实例详情 | PJXExtension | 2_1_R | 参数 {"pi":实例ID}；返回 p |
| 仓库变化通知 | PJXExtension | 2_1_25 | 推送后触发受控只读刷新 |
| 设置背包序列 | PJXExtension | 2_1_11 | {"pps":"ID#ID...","ppt":背包类型} |

官方材料在 D:\奥奇工程\奥奇传说解包 下；具体路径由生成器和 Catalog I/O 解析器选择，不把某一账号的响应当通用定义。

实例身份是“账号 + id”。r/ri 表示种族/形态，fr 是形象；名称、位置、种族或当前所选行都不能充当实例 ID。背包响应可能含详细培养字段，但不能仅凭命令名认定每只对象完整；仓库列表主要是摘要。Repository 区分 partial/complete、驻留和持久化状态，已保存 partial 仍不等于完整培养事实。

### 3.1 培养字段的解释

| 系统 | 字段 | 解释原则 |
|---|---|---|
| 天赋 | ip、gps、gt | 位置敏感序列与评价值；空项/非法整数不移位、不补零 |
| 元魂 | badge | 定义、等级、觉醒及分槽编码；名称来自冻结元数据 |
| 神源兽 | shenjue | 定义、星/阶方案及当前星阶；缺当前值不能补成最大值 |
| 星轮 | astrolabe、astrolabebr | 节点激活/选择及突破标志；缺突破字段保持未知 |
| 星神 | sgs、sgsp | 装备槽与背包；以已审查编码和品质/万变元数据解释 |
| 服务器战力观察 | zdl、xzdl | 当前/普通极限数值，不单独证明培养字段完整 |
| 分项 | czdlv、mzdlv | 维度匹配、严格整数及具体组件缺口 |

当前 Domain 的战力计算会检查分项维度、星神槽、背包与元数据完整性。最高战力和缺口由冻结定义及已知字段推导，不能对所有精灵固定套用“八红星 + 固定加成”。缺少必要条件时相关 known 标志为 false，排序和展示都保留这一状态。

静态字典由 tools/generate_pet_detail_data.py 从官方精灵字典、元魂 SWF/XML、神源兽方案、星轮和星神配置生成，assets 作为嵌入回退。外部 catalog 更新先完整校验，再在 Core 发布不可变快照；失败保留上一个版本。字典条目数随数据更新变化，不在此写死一个历史数量。

商店项目按 shopId、服务器项目 ID、强化类型和允许种族建立身份，不按中文项目名硬编码。成本表达式、重复资源合并、溢出、解锁与限次分别判定；缺成本不自动当免费，缺限次不自动当无限。具体规则以 Domain 及相应 tests 为准。

## 4. 捕获来源与时间证据

当前数据流为：

~~~text
原版 Hook 捕获必要值与来源
  → 有界 InboundEnvelope 队列
  → Core 校验/应用观察
  → Storage 冻结上下文并异步保存
  → Compute 派生/分析
  → GUI 只读投影与工作台
~~~

原版分发始终继续，扩展不篡改服务器消息。捕获队列不足、来源中断或异常不会通过阻塞原版换取扩展完整性，而是明确撤销/失效有关任务。

兼容通过、客户端已登录、收到一个登录命令、拿到某实例 ID、处于某日历日期，是不同层次的证据。SessionSourceEvidence 分开记录身份和顺序；当前生产适配器没有用本地代数或延时冒充经过审查的主机顺序屏障。未知来源不能凭同名响应或“刚好正在等待”变成可信个人写入。

商店与日常周期的 observedAt 和服务器周期有效性独立。每天/每周的组名不证明具体重置时间；未验证周期可以显示只读数值，但不能绿色显示完成或可执行。

原有日常协议限制仍有效：竞技场相关入口不能因需要显示次数就主动触发会改变冷却的请求；缺少已验证只读接口的玩法明确未读取。服务器最终状态不由本地缓存替代。

## 5. 移动与保存

移动不是“未来待做按钮”：现有 Controller/MoveOperation 已有串行状态机、容量与限制检查、满背包替换选择、发送前后只读核对。关系字段本身不统一判为禁止，租借、已确认出阵/队伍等实际限制按当前策略处理。

写入序列只发送一次。响应超时不重复发送，而是用只读列表确认最终状态；账号切换、来源失效或观察不完整时停止继续提交。

写前与写后核对有两个级别：

- **已验证来源**：需要宿主顺序证据（`orderingVerified` 与有序观察）。目前没有生产适配器能提供，这条路径只在测试中出现。
- **读连续性（v1.3 级别，生产环境实际使用）**：会话已识别账号，且读流从未中断（断线、入站溢出、冲突登录、关闭都会永久清除，需重启客户端恢复）；本次移动强制重读的背包和仓库列表都完整、都在这条读流内、仓库晚于背包到达、两边没有同一实例。满足后才写入意图、调用宿主；发送层只对不带已验证来源且有预检版本的写意图开放这一能力，账号或会话变化会撤销尚未执行的许可。写后同样按这一级别重读并核对实际序列。它无法排除“切换账号瞬间迟到的旧封包”这类极端情况，这是与 v1.3 相同的取舍（2026-09-19 由用户确认）。

本地请求 generation 本身不提供服务端因果顺序。

持久化使用冻结账号/目录/版本上下文、账号锁和 QSaveFile。提交、排队、保存成功和失败分别报告；迟到磁盘读取不覆盖较新的网络事实，旧账号写任务只能使用其原上下文，不能重新绑定为当前账号。

## 6. 数据位置、迁移与可恢复性

默认数据根是客户端目录的 KQPetData，继续账号分区/schema 3，不默认迁到 v2 子目录。KQPET_DATA_ROOT 是显式绝对路径覆盖；隔离预览采用独立根。完整目录见 README。

历史 %LOCALAPPDATA%\KQPetInventory\cache-v1.json 文档描述属于早期方案。当前旧源通过 QStandardPaths::GenericDataLocation 解析，并以只读导入方式处理；设置 override 时默认旧源为 {data-root}\legacy-import\cache-v1.json。导入不删除源、不覆盖已有目标事实，完成标记和实际内容摘要用于可重入恢复。

原文缓存只保留一份完整 payload，并计入仍被计算、I/O 或 GUI 持有的引用。摘要、知识版本、Saved 与 resident 不混为一谈。磁盘详情不是 LRU 清理对象；派生索引可以丢弃重建，匹配时必须覆盖原文、元数据、算法与摘要覆盖依赖。

部署、回退、卸载脚本保留个人数据及原版 EXE；运行扩展会更新所选根中的兼容缓存。不能把“部署不写个人文件”解释成“运行时不保存”。日常安装与预览隔离是测试方式，不能声称默认目录已自动隔离。

诊断使用每次运行独立目录与锁，latest.json 为小索引。日志和复制诊断默认脱敏；兼容失败前不初始化 Qt/I/O，故该阶段可能只有内存诊断。关闭流程有界等待，不承诺全部在途任务一定落盘。

## 7. 预算与验收的当前政策

用户要求预算作参考并留余量。当前默认：分析 input 128 MiB、result 128 MiB、Worker total 512 MiB、编译缓存 16 MiB、I/O outstanding 128 MiB、准备超时 120 秒。队列仍有保护和明确失败；不为符合旧的 64/256 MiB 数字牺牲数据、字段或可用性。

常规性能观测预热 1 次、采样 3 次，冷缓存单列；完整矩阵和严格模式按需运行。记录实际计算阶段、候选数、取消、GUI 反应及进程 Private Bytes，逻辑 payload 估计不冒充进程测量。

打包 identity 绑定源码、Profile、加载器和 DLL。自动测试报告不是登录、真实入口或视觉验收；正式发行还需同产物的实际客户端、DPI、回退、原版 EXE 不变与实践性能评审证据。v2 目前以预览版发布（真实客户端交互由用户手动验证）；不能将历史报告或模拟 fixture 当作正式发行通过的依据。
