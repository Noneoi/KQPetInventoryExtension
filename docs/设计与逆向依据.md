# 设计与逆向依据

## 1. 目标边界

本工程直接扩展二进制原版 `KQPro*.exe`；当前验证和部署目录仍是 `氪奇Pro-V1.1.3`。`逆向\逆向` 中的复刻工程仅作为已有逆向报告的证据来源，不是功能承载程序，也不需要带着复刻程序运行。

推荐采用“外置启动器 + 进程内 Qt 扩展 DLL”，原因是原版只有二进制和运行库，没有可重新编译的源工程：

1. 启动器负责自动选择最高版本 `KQPro*.exe`、正常启动原版、调用 `LoadLibraryW` 加载扩展。
2. DLL 运行在原版进程内，因此能使用原版已经创建的 `QApplication` 和主窗口。
3. DLL 捕获原版网页/Flash 到 C++ 的消息入口，同时调用原版自己的 Flash 命令发送函数。
4. UI 是原版 Qt 窗口的子按钮和所属对话框，用户仍然只操作原版登录器。
5. 原版文件不落盘打补丁，删除两个扩展文件即可回退。

## 2. 原版桥接入口

目标原版的 ImageBase 是 `0x140000000`，ASLR 下全部使用“实际模块基址 + RVA”。

| 功能 | 静态地址 | RVA | 本工程用途 |
|---|---:|---:|---|
| WebViewService 单例取得 | `0x140115450` | `0x115450` | 取得原版发送服务对象 |
| `recivedata/cutdata/otherreturn` 分发 | `0x140115920` | `0x115920` | 只读捕获服务器返回 |
| Flash 命令发送 | `0x140116470` | `0x116470` | 复用原版发送精灵查询 |

分发函数推定签名：

```cpp
void __fastcall dispatch(
    quintptr a1,
    quintptr a2,
    quintptr a3,
    const QString& method,
    const QVariantList& arguments);
```

发送函数推定签名：

```cpp
void* __fastcall getWebViewService();
void __fastcall sendCommand(void* service, const QString* wireCommand);
```

`wireCommand` 格式是 `Ext|cmd|json`。原版函数会拆成三段并生成：

```javascript
document.myFlash.senddata('%1','%2',JSON.parse('%3'),'xml',-1);
```

逆向证据在已有文件：

- `D:\奥奇工程\逆向\逆向\reports\ida-bridge-decompiled.txt`
- `D:\奥奇工程\逆向\逆向\reports\bridge-protocol.md`
- `D:\奥奇工程\逆向\逆向\tools\frida_hook_bridge.py`

目标字节已直接从原版 EXE 的 `.text` 节复核：

```text
RVA 0x115920:
48 89 5C 24 10 55 56 57 41 56 41 57 48 8D 6C 24 D1

RVA 0x116470:
48 89 5C 24 18 55 56 57 41 54 41 55 41 56 41 57 48 8D 6C 24 D9
```

DLL 在安装内联钩子前再次比较这些字节；如果更新版 RVA 已变化，则在 PE 可执行代码段中扫描三个唯一签名。扫描不到或出现多个匹配时安全停止，不会按旧偏移强行挂钩。

## 3. 官方精灵协议

这些命令来自 `奥奇传说解包` 中的官方 ActionScript，不是根据字段名猜测。

| 场景 | Ext | cmd | 参数 | 主要返回字段 |
|---|---|---|---|---|
| 读取背包 | `PJXExtension` | `2_1_10` | `{}` | `pps` 背包顺序、`pl` 精灵对象、`ppc` 容量 |

| 设置背包序列 | `PJXExtension` | `2_1_11` | `{"pps":"ID#ID...","ppt":背包类型}` | 后续写操作基础 |

### 3.1 详情字段解析

详情页使用的字段对应关系已逐项和官方 `PetBuild`、progression 类核对：

| 显示系统 | 响应字段 | 官方解析格式 |
|---|---|---|
| 天赋 | `ip / gps / gt` | 12 项最终天赋值 / 星能等级 / 天赋评价等级 |
| 元魂 | `badge` | `职业元魂ID:等级#专属元魂ID:觉醒状态`，槽间用 `|` |
| 神源兽 | `shenjue` | `定义ID#升星方案#升阶方案|当前星:当前阶` |
| 天迹星轮 | `astrolabe` | 节点 `星灵ID:已激活:已选中`；链/节点分别用 `|`、`#` |
| 星轮突破 | `astrolabebr` | 布尔值 |
| 星神 | `sgs` | 槽 `显示星神ID:等级:底座星神ID`；底座为万变金/红星时给显示名称加下划线 |
| 当前战斗力 | `zdl` | 服务器返回的精灵当前总战斗力 |
| 普通极限战斗力 | `xzdl` | 金色星神、天迹星轮未突破基准下的官方极限战斗力 |
| 当前/极限战力分项 | `czdlv` / `mzdlv` | 对比 `iv/sgv/bsv/asv/sjv` 等字段，定位天赋、星神、元魂、星轮、神源兽等具体缺口 |

静态中文名不靠硬编码当前账号样本。`tools/generate_pet_detail_data.py` 从以下官方来源生成 `assets/pet-detail-data.json`：

- `PetDictionaryDataContents(.Update).as`：精灵名、皮肤所属原种族、属性、职业。
- `petbadgeservice SWF` 内嵌 XML：职业元魂与专属元魂名称。
- `SE_SacredEquipmentConfig.as` 以及星/阶升级方案：神源兽名称和满级边界。
- `astrolabeservice SWF` 内嵌 XML：星灵名称。
- `stargodservice SWF` 内嵌 XML：星神名称、品质判定所需配置和万变定义。

生成结果由 `resources.qrc` 嵌入扩展 DLL，既能离线显示，也避免每次启动扫描整个解包目录。当前字典覆盖 9542 条精灵图鉴、644 条元魂配置、75 只神源兽、480 个星轮节点和 89 条星神/星元定义。

## 4. 数据流

```text
KQPetLauncher.exe
  └─ 自动选择并启动最高版本 KQPro*.exe
      └─ 加载 KQPetInventory.dll
          ├─ 给原版主窗挂“精灵仓库”按钮
          ├─ 调原版 sendCommand
          │   ├─ 2_1_10 读取背包
          │   ├─ 2_1_S 读取仓库
          │   └─ 2_1_R 读取单只仓库详情
          └─ 捕获原版 dispatch/recivedata
              ├─ 更新内存模型
              ├─ 原子写入账号分区缓存
              └─ 刷新原版所属的精灵窗口
```

钩子先复制消息参数，随后调用原版函数，最后把副本交给仓库模型。扩展不截断、不篡改服务器消息，原版本身仍会照常处理同一返回。

## 5. 缓存策略

缓存路径是 `%LOCALAPPDATA%\KQPetInventory\cache-v1.json`，格式要点：

```json
{
  "schema": 1,
  "lastAccount": "账号ID",
  "profiles": {
    "账号ID": {
      "savedAt": "ISO-8601 时间",
      "backpack": [],
      "warehouse": [],
      "details": {}
    }
  }
}
```

- `21_1` 返回中的 `info.n` 用作账号分区键。
- 启动时先显示最后一次本地数据，线上响应到达后覆盖。
- 使用 `QSaveFile`，写完成功后才替换旧缓存，降低进程意外退出导致 JSON 损坏的风险。
- 缓存只用于展示；服务器始终是后续写操作的最终事实来源。

## 6. 后续一键入库/进背包方案

官方 `PetDataService` 表明，入库和进背包都以 `2_1_11` 更新某个背包类型的 `pps` 序列完成：

- 入库：从目标 `pps` 删除所选实例 ID，再提交新序列。
- 进背包：把仓库实例 ID 加到目标 `pps`，再提交新序列。

不建议把“全部”实现成无校验的单条字符串操作。推荐流程：

1. 写操作前强制刷新 `2_1_10 + 2_1_S`，不用陈旧缓存计算。
2. 根据 `ppc` 检查目标背包容量。
3. 排除出战阵型、跟随、召唤/被召唤、携带/被携带、租借等官方限制状态。
4. 生成变更预览，让用户看到成功数量与被跳过原因。
5. 每个背包类型串行提交 `2_1_11`，等待对应响应后再处理下一类。
6. 任一步失败就停止后续提交并重新刷新，不能继续基于旧序列操作。
7. 最后重新读取背包和仓库，服务器返回一致后才报告完成。

当前工程刻意只交付读取、缓存和详情，先用真实账号验证字段和 UI。等读取证据确认后，再加写按钮与上述事务状态机，可以显著降低错序列导致精灵位置异常的风险。

## 7. 已知限制

- 启动器自动选择同目录版本号最高的 `KQPro*.exe`，不绑定固定 SHA-256；协议入口签名未变化的更新版可以直接使用，签名变化时需要更新扩展签名。
- 必须用与原版 ABI 一致的 Qt 6.6.3 开发包编译。
- 进程注入和内联钩子可能被安全软件提示；代码未修改原版磁盘文件，但运行时属于进程扩展。
- 当前环境已安装 Qt 6.6.3 `msvc2019_64` 与 MSVC x64 工具链；启动器和扩展 DLL 均已完成 Release 编译。原版自带的 `Qt6Core/Qt6Gui/Qt6Widgets` 文件版本也已核对为 `6.6.3.0`。
