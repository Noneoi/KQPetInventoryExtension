## 0. 一句话结论

游戏**只有一个战力公式**，它不按“时代”写死，而是按**精灵身上的官方时代标签（`sign`）+ 该精灵实际存在的培养序列**决定哪些系统参与计算。因此“各时代战力算法不同”，在官方实现里的真实形态是：

- **总战力 = 11 个分项之和**（等级、天赋、潜能、星神、装备、守护石、学习力、传说石、元魂、星轮、神源兽）；
- 其中 **9 个分项是“真培养系统”**，另外 2 个（守护石、学习力）在 **2017-06-09 神职时代被官方移除**，字段保留但恒为 0；
- 时代差异体现为 **系统开关**（哪些分项非零）、**上限**（等级上限 / 星神槽数 / 星神槽等级 / 元魂等级档位）、以及 **旧系统被新系统替代**（源兽→源兽神觉、传说石→神运技、守护石/学习力→删除）。

## 3. 总公式（官方唯一实现）

### 3.1 当前战斗力

`mmo.interfaces.pet.data.PetBuild::get battlePower`（**权威聚合公式，直接照抄官方源码**）：

```text
战力 = Σ(所有 "effective" 培养项的当前战力)
       − 等级项 − 天赋项
       + 等级 × (种族基础战力 BasicZhanDouLi + 有效天赋合计 × 3) ÷ 200
```

其中第三行是一个**合并项**：官方把「等级」与「天赋」合成一项后**只截断一次**，而服务端分项 `czdlv.lv` / `czdlv.iv` 是**各自截断**的。所以：

```text
zdl = Σ(11 个分项) − czdlv.lv − czdlv.iv + trunc(等级 × (BasicZhanDouLi + 天赋合计 × 3) ÷ 200)
```

**这个公式是精确的、可完全复现的，不是「差 0 或 1」的经验规律**：

| 复算方式 | 与官方 `zdl` 一致 |
|---|---|
| 用回包的 `czdlv.lv` / `czdlv.iv` 代入上式 | **1465 / 1465** ✅ 零例外 |
| **用我自己解包的表算出的 `lv` / `iv` 代入上式** | **1465 / 1465** ✅ 零例外 |

而「Σ11 分项本身」与 `zdl` 的关系才是 0/1 差：

| 关系 | 条数 |
|---|---|
| `zdl == Σ11 分项`（截断没丢位） | **1034** |
| `zdl == Σ11 分项 + 1`（两次截断各丢一次小数） | **431** |
| 其它差值 | **0** |

> 数学上必然如此：`trunc(a) + trunc(b) ≤ trunc(a+b) ≤ trunc(a) + trunc(b) + 1`。但**别把它当成规律去用** —— 只要按上面的合并式算，就是 1465/1465 精确命中。

### 3.2 极限战斗力

`PetBuild::get extremeBattlePower` = `Σ(每个 "effective" 培养项的 getBattlePowerMax())`。

- **没有合并项**（不像当前战力那样把等级/天赋合并再截断）
- **只累加 `effective == true` 的分项**（`PetBuild.progressions` 会先按 `effective` 过滤），所以某个 `sequence` 为空的分项直接不参与

实测 **1465/1465 条与官方 `xzdl` 完全相等（0 误差）**。

⚠️ 关键性质：**`xzdl` 不是“理论最大值”**，而是“服务端硬编码上限之和”。例如天赋用的是固定系数 540/700（而非按星能 1.5× 算出的 600），星神用的是金色星神定义 51 的逐级表，灵初的星轮突破 +150 **不计入 `xzdl`**。

### 4.1 逐项展开

#### ① `lv` 等级与基础成长

- 公式：`等级 × BasicZhanDouLi ÷ 200`（`BasicZhanDouLi` 来自官方精灵数据 XML 的 `BasicZhanDouLi` 字段）。
- 上限：`该种族最大等级 × BasicZhanDouLi ÷ 200`。
- 时代差异：**只由等级上限决定**（各时代等级上限的取值来源见 §2.2.2；逐时代明细见 §8）。

#### ② `iv` 天赋（星能）

官方 `PetGift.as` + `PetProgressionGifted.as`。**这一项的字段链最容易搞错，完整链条如下（已逐轨 17580/17580 验证）**：

| 回包字段 | 官方语义 | 公式 / 说明 |
|---|---|---|
| `ip` | 12 轨**最终天赋值**（`#` 分隔） | = `floor(raw × 系数)`，取值 0–120 |
| `gps` | 12 轨**星能等级**（`#` 分隔） | 取值 **1 / 2 / 3**；**回包里可能整个字段缺失**（本样本 1003/1465 条缺失），缺失时 `setStars("")` 走 else 分支 → 12 轨系数**全为 1** |
| `raw`（派生） | 12 轨**原始值** | = `Math.ceil(ip ÷ 系数)`，**恒 ≤ 80**（`RAW_LANE_MAX_VALUE`） |
| 系数（派生） | 星能加成 | `STARS_COEFFICIENT[gps]`，表 = `[1, 1, 1.25, 1.5]` → 星能等级 1 = ×1，2 = ×1.25，3 = ×1.5 |
| `ss`（回包） | 12 轨**星级**（1–6） | = `getStarCountsByValue(raw)`，阈值 `VALUE2STAR = [0,11,21,31,51,63]` |

**验证结果（全 1465 条 × 12 轨 = 17580 轨，逐轨复核）**：

| 断言 | 结果 |
|---|---|
| `raw = ceil(ip ÷ 系数[gps]) ≤ 80` | **17580 / 17580**，零例外（`raw` 实测范围 0–80，其中 2049 轨恰好为 80） |
| `ss = getStarCountsByValue(ceil(ip ÷ 系数[gps]))` | **17580 / 17580**，零例外 |
| `floor(ceil(ip ÷ 系数) × 系数) == ip`（即 `ip` 已是合法最终值） | **17580 / 17580**，零例外 |
| `iv = trunc(等级 × 有效天赋合计 × 3 ÷ 200)`，合计用 `ip` 或官方反推式 | **1465 / 1465**，两种算法结果一致 |

> ⚠️ **`ss` 不能直接用 `ip` 推**：必须先把 `ip` 除回原始值。直接 `getStarCountsByValue(ip)` 只有 **17573/17580**（7 轨错，都是 `ip` 恰好在阈值上、但除回原始值后掉档，如 `ip=63, gps=2 → raw=51 → 5 星` 而非 6 星）。

**轨道规则（时代的真正分水岭）**：

- 12 条天赋轨道顺序：`生命, 物攻, 物防, 魔攻, 魔防, 超攻, 超防, 速度, 超物攻, 超物防, 超魔攻, 超魔防`
- `BEFORE_GODJOB`（攻击类型 = 物攻 / 魔攻）：`生命, 物攻, 物防, 魔攻, 魔防, 超攻, 超防, 速度` — **8 条**
- `AFTER_GODJOB`（攻击类型 = 超物攻 / 超魔攻）：`生命, 速度, 超物攻, 超物防, 超魔攻, 超魔防` — **6 条**
- **有效天赋合计** = 所属轨道里，`非攻击轨道全部计入 + 攻击轨道只计入与自身攻击类型相同的那一条`
  - 8 轨道精灵 → **7 条计入**（= 8 − 2 条攻击轨 + 1 条匹配）
  - 6 轨道精灵 → **5 条计入**（= 6 − 2 + 1）
- 战力 = `等级 × 有效天赋合计 × 3 ÷ 200`（**整除截断**）

> 这套“8 轨道 → 6 轨道”的切换，就是**神职时代属性大翻新的战力侧体现**。官方公告原文：
> 「神职后精灵属性大翻新：物攻→超物攻、物防→超物防、魔攻→超魔攻、魔防→超魔防…… 神职业精灵能力分为：超物攻、超物防、超魔攻、超魔防、生命、速度。」
> —— <http://aoqi.100bt.com/xinwen/257419.html>（2017-01-04）

**实测校验（灵初 120 级实例，回包原值）**：
`ip = 100#0#0#0#0#0#0#120#100#120#100#100`，`gps = 2#1#1#1#1#1#1#3#2#3#2#2`（该组合在样本中命中 **12 条**，如「机战环穹·哆啦」race 6490）
→ 计入轨道 = 生命100 + 速度120 + 超物防120 + 超魔攻100 + 超魔防100 = **540**
→ `iv = 120 × 540 × 3 ÷ 200 = 972`，与服务器 `czdlv.iv = 972` 完全一致 ✔

> 另注：该精灵 `ss = 6#1#1#1#1#1#1#6#6#6#6#6`；轨 0 的 `raw = ceil(100÷1.25) = 80` → 6 星 ✔，轨 1 的 `ip=0` → `raw=0` → `getStarCountsByValue(0) = 1`（`VALUE2STAR[0]=0`，从后往前找第一个 `raw >= 阈值` 的档，返回 **index+1**，故 0 就是 1 星）。回包 `ss=1` 与函数本身一致，**没有**另一层「显示下限钳制」。

### 5.1 上表的证据分级 —— 硬门槛 vs 数据驱动

矩阵里每一格「某时代某系统开放/关闭」有**两类完全不同的成因**，必须分开，否则会误以为「时代代码里写死了元魂从启元开始」：

**A 类｜硬代码门槛（`switch` 在 `PetDictionaryDataItem` 的时代判定上）**

只有 **5 个**时代判定函数真正参与了战力公式的开关：

| 判定 | 出现位置（自解包源码） | 作用 |
|---|---|---|
| `isGodJob()` | `PetProgressionGifted.as:125` → `_loc3_ = _loc1_.isGodJob() ? 540 : 700;`<br>`PetProgressionEquipment.as:65` → `if(!pddi.isGodJob() \|\| pddi.isShenYun())` | 天赋极限档位 **540 / 700**；**源兽装备 `ep` 的准入** |
| `isLegend()` | `PetProgressionProficient.as:79` → `return _loc1_.isLegend() ? 0 : 400;`<br>`PetProgressionStone.as:70,94` → `if(!pdi.isLegend() \|\| pdi.isShenYun())`<br>`PetProgressionStone.as:118` → `if(_loc1_.isLegend())` | 潜能极限**归零**；**传说石 `lsv` 的准入**；传说石档位组 |
| `isTianQi()` | `PetProgressionStone.as:114` → `if(_loc1_.isTianQi())` | 传说石档位切到 **1850** 组 |
| `isShenYun()` | `PetProgressionEquipment.as:65`、`PetProgressionStone.as:70,94` | **一票否决** `ep` 与 `lsv`（两个系统同时关闭） |
| `isQiYuan()` | `PetDictionaryDataItem.as:1049,1115,1125`（星神槽数组构造）<br>`IdealHypotheticalPet.as:115` → `_stargod.setChangeable(this.dictData.isQiYuan())` | 星神槽 **+1**（万变格） |

**B 类｜数据驱动（无时代判定，只看该精灵有没有对应的 `sequence` 字段）**

`PetProgression` 基类及其子类的 `effective` getter 决定该分项是否计入总战力：

```
PetProgressionStargod.as:31        return !StringUtil.isNullOrEmpty(this._sequence);          // sgv
PetProgressionAstrolabe.as:30      return !StringUtil.isNullOrEmpty(this._sequence);          // asv
PetProgressionStone.as:35          return !StringUtil.isNullOrEmpty(this._sequence);          // lsv
PetProgressionBadge.as:30          return !StringUtil.isNullOrEmpty(this._sequence);          // 徽章
PetProgressionSacredEquipment.as:30 return !StringUtil.isNullOrEmpty(this._sequence);         // 圣装
PetProgressionEquipment.as:29      return !isNullOrEmpty(this._sequence) && this._sequence != "0,0,0";  // ep
```

配合 `PetProgression.as:57` → `this._battlePower_C = this.effective ? this.runBattlePower() : 0;`，**只要服务端下发的 `sequence` 为空，该分项就恒为 0，与精灵属于哪个时代无关**。

> **结论（重要）**：`ep` 例外 —— 它**同时**受 A 类与 B 类约束（且约束点不同，见下）；而 **`bsv`（元魂）、`asv`（星轮）、`sjv`（神源兽）三个分项的「时代起点」完全是服务端数据行为**，客户端代码里**没有**任何 `if(时代 >= 启元)` 之类的判断。矩阵中「元魂从启元开始」是**观测到的下发规律**，不是**代码写死的规则**。

**`ep` 的双重门槛细节（容易搞错的一点）**：

`isGodJob()` **只出现在 `runBattlePowerMax()`（极限值）里**，`runBattlePower()`（当前值）里没有：

```
PetProgressionEquipment.as:54-58   runBattlePower()     → 直接 getBattlePowerBySeq(_sequence, raceId)   ← 无时代判断
PetProgressionEquipment.as:60-68   runBattlePowerMax()  → if(!pddi.isGodJob() || pddi.isShenYun()) return 0;  ← 有时代判断
```

所以当前 `ep` **只**由 `effective` 决定。实测证据：**817 条记录的 `eps` 字符串非空但恰好等于 `"0,0,0"`**（分布：超神 60、神运 129、灵初 225、无标签 345、神属 58），全部被 `!= "0,0,0"` 这一条挡掉，`mzdlv.ep` 均为 0。这正是「服务端对全部精灵都下发 `eps` 字段、无装备时填 `0,0,0`」的直接证据。

> 也就是说：若服务端给一只**神属**精灵下发了**真实**的 `eps`（非 `"0,0,0"`），客户端会**照算当前 `ep`**（`runBattlePower` 无门槛），但**极限 `ep` 仍为 0**（`runBattlePowerMax` 被 `isGodJob()` 拦截）。**当前值与极限值适用不同规则**，不能混为一谈。

> ⚠️ **不要用 `recYuanSou` 自己推上限**。客户端 `PetProgressionEquipment.runBattlePowerMax` 用 `recYuanSou × 星级6` 组装，但服务端口径不是这个：
> 对 1465 条实测样本，`recYuanSou` 推导只能对上 1440 条（98.3%），差异集中在
> ① **皮肤换肤精灵**（`getSwitchSkinPetRaceIds()` 会把种族换成原种族再去匹配专属列表，缺这份数据时必然判错）；
> ② 部分旧传说精灵的专属判定。
> 改用官方 `YuanSou` 字段（空则 3600）后 **648/648 完全一致、0 例外**。
>
> **`ep` 当前值的公式已被独立复算验证**：`E4PV2_EInfo.getBattlePowerByRace`
> = `base(按攻击类型) × 星级 + (该种族命中专属列表 ? ex : 0)`，
> 逐槽展开见 `各时代战力逐点构成.md` 的「⑤ 源兽装备逐槽明细」。1465/1465 全中。

**公式**（`E4PV2_EInfo.getBattlePowerByRace`）：

```text
atk = 该精灵的攻击类型（超物攻 / 超魔攻 / 旧物攻 / 旧魔攻）
ex  = 该种族命中该源兽的专属列表（需先做皮肤/多形态重映射）
单槽战力 = (atk==超物攻 ? basePhy : atk==超魔攻 ? baseMag : 0) × 该槽星级
         + (ex ? (atk==超物攻 ? exPhy : exMag) : 0)
```

> ⚠️ **`recYuanSou` 组装结果【不等于】官方 `YuanSou` 字段**（本文 v1.3 更正）：全字典 9638 只里两者都有的是 2510 只，复算只对上 **1575/2510**（62.7%）。所以**不能拿 `recYuanSou` 当上限**，必须用 `petdata.YuanSou`（空 ⇒ 3600），那条路是 **1465/1465**。

### 7.6 传说石（`legend/legendservice`，本次新解包）

`LgsConfig.as` 给出了 **23 条定义**（4 种碎片 + 18 种传说石 + 变身传说石），每条 5 级：

| 传说石 | 组 | L1 | L2 | L3 | L4 | L5 |
|---|---|---:|---:|---:|---:|---:|
| 物伤 / 魔伤 传说石 | 1 | 14※ | 28※ | 42※ | 56※ | 70※ |
| 暴伤 / 连击伤害 / 群攻伤害 传说石 | 1 | 14 | 28 | 42 | 56 | 70 |
| 物抗 / 魔抗 / 格挡减伤 / 溅射减伤 传说石 | 2 | 14 | 28 | 42 | 56 | 70 |
| 生命 / 暴击 / 命中 / 破击 / 闪避 / 格挡 / 防暴 传说石 | 3 | 14 | 28 | 42 | 56 | 70 |
| 回血 / 治疗 / 变身 传说石 | 4 | 14 | 28 | 42 | 56 | 70 |

※ **唯二的条件式**，全 23 条定义里只有 **id 5（物伤）与 id 6（魔伤）** 是这种形式，实际存储为 `"A#B"`：

```text
canBeInstalledByDicData(pet):
   无 "#" → true（任何精灵都能装）
   有 "#" → required = PetAttackType.valueOfId(A)     // 1=物攻 2=魔攻 3=超物攻 4=超魔攻
            return 精灵主职业.attackType == required || 精灵副职业.attackType == required

getBattlePowerByRace(raceId):
   无 "#" → 返回该值
   有 "#" → canBeInstalled ? int(B) : 0
```

即 **`"3#14"` = 前缀 3 → 要求「超物攻」，匹配才给 14，否则该石战力为 0**；`"4#14"` 要求「超魔攻」。

| 石 | 定义 ID | 存储值 | 要求的攻击类型 |
|---|---|---:|---|
| 物伤传说石 | **5** | `3#14 / 3#28 / 3#42 / 3#56 / 3#70` | **超物攻** |
| 魔伤传说石 | **6** | `4#14 / 4#28 / 4#42 / 4#56 / 4#70` | **超魔攻** |

> **实测**：样本里 stone 5 被用 **443** 次、stone 6 被用 **242** 次，**攻击类型 100% 匹配、0 例外** —— 所以这条门槛在样本上不改变结果（加不加都是 1465/1465），但**规则必须按此实现**。


**传说石分项 `lsv` 的完整分解**（`runBattlePowerMax` 里的 1350 / 1850 由此而来）：

```text
lsv = 传说技档位战力 + Σ 5 个石槽的逐级战力
    = 传说技档位战力 + 5 × 70（5 槽全 5 级）= 传说技 + 350
```

**传说技档位**来自 `formation/formationservice` 的 `LegendSkillConfig.as`（**3503 条档位定义、584 个技能**），按「红/黄（或指定组）传说石总等级」分档：

| 时代 | 0–4 | 5–9 | 10–14 | 15–19 | 20–24 | 25（满槽满级） |
|---|---:|---:|---:|---:|---:|---:|
| **传说时代**（**144** 个技能用此档） | 0 | **200** | **400** | **600** | **800** | **1000** |
| **天启及以后**（**439** 个技能用此档） | 0 | **300** | **600** | **900** | **1200** | **1500** |

**所以：**

```text
传说时代 lsv 极限 = 1000 + 350 = 1350   ← 与官方 mzdlv.lsv 逐条一致
天启及以后 lsv 极限 = 1500 + 350 = 1850 ← 与官方 mzdlv.lsv 逐条一致
神运及以后 = 0   ← 原因是 lss 为空 → effective=false（B 类数据驱动），不是 isShenYun() 代码判断
```

> **各技能的最大档位实测分布（584 个技能）**：最大 **1000** → **144** 个；最大 **1500** → **440** 个（其中 **1 个技能只有 5 档**：`300/600/900/1200/1500`，没有 0 档；其余 439 个是 `0/300/600/900/1200/1500`）。合计 **584**，无第三种。
>
> 档位算法的源码语义（`LegendSkillDefine.computeLevelSum` + `getLegendSkillDefineAvailable`）：
> - `levelSum` 一律用**该技能第一条定义** `skillDefines[0]` 的 `trigger` 计算，与当前档位无关
> - `trigger=1` 按**石的 `group.id`** 匹配求和；`trigger=2` 按**石的 `defineId`** 匹配求和
> - 档位匹配**从最后一条往前找**，返回第一个满足 `triggerParam` 冒号后 `lo-hi` 区间包含 `levelSum` 的

> 同一传说石的 `battlePower` 与「属性效果百分比」是两套数：效果见 `desc`/`prop`，战力只看上面的表。

### 7.7 天赋（星能）

| 项 | 值 |
|---|---|
| 单条**原始值** `raw` 上限 | **80**（`RAW_LANE_MAX_VALUE`，实测 17580/17580 轨道全部 ≤ 80） |
| 星能系数 `STARS_COEFFICIENT` | `[1, 1, **1.25**, **1.5**]`，由 `gps` 索引（1 → ×1，2 → ×1.25，3 → ×1.5） |

## 9. 常见问答（直接可引用的结论）

**Q1：一颗红星加多少战力？**
A：看它装在几级星神槽。红星（quality 6）逐级战力为 `1级140 / 2级210 / 3级280 / 4级350 / 5级420 / 6级490 / 7级570 / 8级650`。所以 6 级槽 +490，8 级槽 +650。灵初精灵装满 8 个 8 级红星时，星神分项 = **5200**。

**Q2：一颗金星加多少战力？**
A：`1级100 / 2级150 / 3级200 / 4级250 / 5级300 / 6级350 / 7级425 / 8级500`。但官方**极限战斗力**从不按金星算真实值，而是按「金色星神定义 51（气吞山河）」在该精灵槽位等级上限下的战力 × 槽数。

**Q3：万变红星比普通红星多/少多少战力？**
A：**完全相同**。万变红星（定义 80）与普通红星共用同一张表，差异只在「可自由换色」，战力按所在槽位等级结算。

**Q4：一个专属元魂（觉醒）加多少战力？**
A：**固定 +200**，615 种专属元魂全部 200。

**Q5：一级职业元魂、五级职业元魂、七级职业元魂各多少战力？**
A：旧档 `120/级` 上限 5 级（满 600）；神运档 `200/级` 上限 5 级（满 1000）；灵初档 `200/级` 上限 7 级（满 1400）。

**Q6：一颗传说石加多少战力？**
A：**逐级固定**：`1级14 / 2级28 / 3级42 / 4级56 / 5级70`（18 种传说石全部同表，只有物伤/魔伤两种是「可装备才给值」的条件式）。**5 槽全 5 级 = 350**。
整条 `lsv` = **传说技档位 + 350**；传说技档位按「红/黄传说石总等级」分档：
- 传说时代：`0 / 200 / 400 / 600 / 800 / 1000`（总等级 0-4 / 5-9 / 10-14 / 15-19 / 20-24 / 25）—— **144** 个技能
- 天启及以后：`0 / 300 / 600 / 900 / 1200 / 1500` —— **439** 个技能（另 1 个技能只有 5 档 `300…1500`）
→ 传说极限 `1000 + 350 = 1350`，天启极限 `1500 + 350 = 1850`，神运及以后 `0`（因 `lss` 为空 → `effective=false`）。

**Q6b：一只精灵的源兽装备分项最多加多少战力？**
A：**直接查官方 `petdata` 表的 `YuanSou` 字段**，取值只有 5 档：**4500**（2420 只）/ 4320（10 只）/ 4200（43 只）/ 3960（19 只）/ 3600（21 只）。神职时代起开放，神运时代起被源兽神觉取代（归零）。

**Q7：为什么我的精灵「战斗力」比「极限战斗力」还高？**

A：1465 条样本里共 **268 条** `zdl > xzdl`，**全部由下面两个原因之一（或两者叠加）造成**，且满足精确恒等式：

```
zdl - xzdl  ==  Σ (czdlv[k] - mzdlv[k])        268 / 268 成立，零例外
```

| 原因 | 分项 | 条数 | 机制 |
|---|---|---|---|
| **A. 星神装了红星，超过官方参考值** | `sgv` | 269 | 官方极限 `mzdlv.sgv` 用的是**金色定义 51「气吞山河」**在槽位上限等级的战力；而**红色星神**（质量 6）在同等级更高，于是实际值超过官方「极限」 |
| **B. 灵初星轮突破 +150 未计入官方极限** | `asv` | 220 | `czdlv.asv` 含突破的 `+150`，官方 `mzdlv.asv` **不含**，故恒差 150 |

**原因 A 的精确算式**：官方极限是 `槽数 × 金色定义51「气吞山河」在「该精灵槽位等级上限」下的战力`；红星（质量 6）在同一等级更高，于是超出。**已验证恒等式（1465/1465 成立，零例外）**：

```
czdlv.sgv − mzdlv.sgv  ==  Σ槽 ( 实际星神战力 − 金色定义51@槽位上限战力 )
```

**单槽偏差的全部取值（全样本 1465 只精灵、共 7424 个槽位，逐槽清点）**：

| 槽位等级上限 | 槽内星神 | 等级 | 该槽战力 | 官方参考（金 51） | 单槽偏差 |
|---:|---|---:|---:|---:|---:|
| 6（神职 ~ 神运） | **红色**（气贯星河/千杀破云/神圣命魂/反守为攻…） | 6（满） | 490 | 350 | **+140** |
| 8（灵初） | **红色**（同上 + 凌波微步/福虎佑灵/守御圣印/乘怒裂穹/万变红星） | 8（满） | 650 | 500 | **+150** |

- **单槽的正偏差只有 +140 与 +150 两种**，其余情况（装金色满级）偏差为 **0**，等级不满则为负值。
- 因此**红星的净收益**是：神运级精灵每颗满级红星比金色参考多 **140**；灵初精灵每颗满级红星比金色参考多 **150**。
- ⚠️ **整只精灵的超出额不是固定的 140/150 倍数**：因为它是 Σ 各槽偏差，槽内装金色/不满级的槽会拉低总和，所以净超出额可以是 140~1200 之间的多种取值（实测出现 350、490、660、810 等非 140/150 倍数）。要精确算出某只精灵的超出额，必须**逐槽**求和。

> 实测吻合：`灼灼此夜·黄金`（神运 7 槽全红 6 级）`sgv = 3430 = 7 × 490`，比官方极限 `7 × 350 = 2450` 多 980；`岩风荒原·泰德`（灵初 8 槽全红 8 级）`sgv = 5200 = 8 × 650`，比官方极限 `8 × 500 = 4000` 多 1200。


**原因 B 的精确算式**：全样本 `asv` 当前 > 极限的 **220 条，超出额全部恰好为 150，且 `astrolabebr` 全部为 `true`**（`brk=false` 却超出的：**0 条**）。即
```
czdlv.asv - mzdlv.asv == (astrolabebr ? 150 : 0)
```
> 反向确认：`爱意倾怀·启` 的 `astrolabebr = true` 但 `asv` 当前 2450 < 极限 2700（差 −250），因为它的第 6 条链 `478:0:0` **未点亮** —— 说明突破的 `+150` 与「节点是否点满」是**两件独立的事**。

**其余 9 个分项在全部 1465 条中「当前值恒 ≤ 极限值」（0 条例外）**，所以战斗力不可能因为 `lv`/`iv`/`pl`/`ep`/`lsv`/`bsv`/`sjv` 而高于极限。

**Q8：为什么官方 `zdl` 有时比分项加起来多 1 点？**

A：官方把「等级 + 天赋」合并为一项整体截断（`等级 × (种族基础战力 + 天赋合计×3) ÷ 200`），而 `czdlv.lv` 与 `czdlv.iv` 是分别截断的，两次截断会各丢一次小数。差值**只能是 0 或 1**（实测 **431/1465** 为 +1，其余 1034 条为 0，**无第三种差值**）。


**Q9：老精灵（初始/超进化/神属）为什么战斗力上限特别低？**
A：三层原因叠加：① 等级上限只有 **100**（现代精灵 120）；② 星神槽只有 **3**（现代 8）；③ 没有源兽装备、传说石、元魂、星轮、神源兽这五个大分项（合计现代可占 1.5 万以上战力）。

**Q10：学习力、守护石还有用吗？**
A：**没有**。2017-06-09 起官方移除养成，「战斗力不变」；客户端里已经没有对应的 `PetProgression` 子类，`czdlv.lav` / `czdlv.gsv` 在所有实测样本中恒为 0。

## 10. 精度与踩坑提示

1. **极限 `xzdl` 不是理论最大值**：天赋用 540/700 硬编码（理论上神职精灵可达 600），星神用金色定义 51（不是红星），星轮不含突破 +150。
2. **`sgv` 由槽位等级决定，不由星神本身决定**。同一颗红星换到低等级槽会掉战力；星神背包（`sgsp`）里的星神**不计入当前战力**。
3. **空槽编码有两种**：`0`/`0:等级` 是空普通槽，`-2`/`-2:等级` 是空万变槽。`PetStarGodSlot.valueOf()` 还会把 4 字段旧格式和 `defineIdSource<=0` 的三字段格式规范化。
4. **万变槽的显示与来源分离**：`78:8:80` 表示显示定义 78、来源万变红星 80；战力按显示定义算，但「是否拥有万变红星」要按来源算。
5. **元魂专属槽「已拥有」≠「已觉醒」**：当前战力只认 `isActivateExclusive`，极限值无条件计入。两者相差 200/槽。
6. **星轮的「点亮」与「选中」是两件事**：点亮进战力，选中只决定是否凑满 3 个吃 150 加成的门槛。
7. **传说石与传说技是两段相加**：`legendSkill.battlePower` + 5 个石槽的逐级战力。只数石槽会少算一段。
8. **`sign` 标签是累计集合，字符串顺序不是时间顺序**。判定时代要用 §2.2 的时间顺序取最高代；用字符串顺序会把「神属」误判成比「神职」晚。
9. **`超神不清空` 与 `超神` 同时存在时**，`超神不清空`（3 槽）优先级更高——这是 `STAR_GOD_SLOT_OPEN_LEVEL_DEFINES` 的数组顺序决定的，不是笔误。
10. **别按时代名硬编码槽位**：槽数由 `sign` 标签组合（`六星神`/`七星神`/`星级N/3`/`启元`/`超神不清空`）共同决定。例如「六星神 + 启元」是 7 槽，不是 6 槽。

### 16.5 传说石的攻击类型门槛（本轮新查出）

`LgsItemLevelDefine.battlePower` 可以是 `"A#B"` 形式。**`A` 不是种族、是 `PetAttackType.valueOfId` 的攻击类型编号**：

```text
canBeInstalledByDicData(pet):
   若该石 1 级的 battlePower 不含 "#" → 任何精灵都可装
   否则 required = PetAttackType.valueOfId(A)          // 1=物攻 2=魔攻 3=超物攻 4=超魔攻
         return 精灵主职业.attackType == required || 精灵副职业.attackType == required

getBattlePowerByRace(raceId):
   无 "#" → 直接返回该值
   有 "#" → canBeInstalled ? int(B) : 0                ← 不匹配则【该石战力为 0】
```

全表只有 **2 种石**是 `"A#B"`：**物伤传说石（id 5，`3#14`…`3#70`，要求超物攻）** 与 **魔伤传说石（id 6，`4#14`…`4#70`，要求超魔攻）**；其余 21 种都是平铺的 `14/28/42/56/70`。

**实测**：样本中 stone 5 被使用 **443** 次、stone 6 被使用 **242** 次，**攻击类型全部匹配，0 例外** —— 所以这条门槛在样本上不改变结果（1465/1465 依旧），但**规则必须按此实现**，否则给超魔攻精灵装物伤石会多算 70。

### 16.6 传说技档位算法的源码确认

### 18.6 ★ 解包产物的版本校验（本节最重要的自查）

§18.1–18.5 都在比对「我的 JSON ← 我的解包产物」。但还有一个更前提的问题：**我的解包产物本身是不是官方当前版本？**

**校验方法**（两步，缺一不可）：

```text
1) curl https://aoqi.100bt.com/play/start.xml
     → <v> 给出 startVersion，<u> 给出【热更清单】（会覆盖 versiondata 里的版本）
2) curl https://aoqi.100bt.com/play/versiondata~<startVersion>.swf
     → -export binaryData 拿到完整模块清单 <f n="模块路径" v="版本号"/>
   有效版本 = 清单 ← 被 start.xml 的 <u> 热更覆盖
   然后逐个比对：本地 SWF 文件名本体 == 模块路径 且 文件名里的版本号 == 有效版本
```

> ⚠️ **解析坑**：`<f>` 的**属性顺序不固定**，会写成 `<f m="…" n="…" s="…" v="…"/>` 或 `<f n="…" v="…"/>`。
> 用 `<f\s+n="…"\s+v="…"` 这种要求「n 紧跟 v」的正则，会**漏掉大量条目**（实测 23567 个 `<f>` 里会漏掉绝大部分），从而误判为「清单里没有这个模块」。
