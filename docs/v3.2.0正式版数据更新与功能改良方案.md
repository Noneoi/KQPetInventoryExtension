## 二 当前数据更新值得优先改的地方

| 当前源码事实 | 可能影响 | 改良方向 |
|---|---|---|
| Flash 入口优先取 `lv`，其次才取 `v`；版本表缓存主要绑定入口版本 | 需要核对实际加载版本与覆盖规则，避免读到不适用的版本表 | 统一官方加载链解析，覆盖 `v` 与 `lv` 不同、`u.f` 覆盖等场景 |
| 技能更新发现 H5 总版本相同且数量达标，就在读取当前资源表和覆盖项之前返回 | 总版本不变但文件覆盖、解析规则或内容发生变化时，可能漏检查 | 比较实际使用的资源身份和规则身份，不只看 H5 总版本 |
| 单类 AS 导出及活动整模块导出没有共用持久导出缓存 | 进入重解析路径后，可能重复启动 Java 和导出相同内容 | 增加按真实来源、工具和导出范围绑定的提取缓存 |
| 六类资料分别原子写回各自文件 | 单文件写入可靠，但关联目录可能处于不同更新批次 | 先生成候选，再按实际依赖组校验与应用 |
| 结果主要通过进度文本和错误字符串传给界面 | 部分更新成功与部分警告容易混在一起，重试范围不明确 | 持久记录任务和各类别状态，区分已检查、已保存及已载入 |
| 单独更新技能也会先执行公共 Flash 版本获取 | 不相关来源不可用时，可能阻断原本独立的技能检查 | 按类别实际需要准备 Flash 或 H5 来源，避免无关前置条件 |

源码入口：[通用更新器](https://github.com/Noneoi/KQPetInventoryExtension/blob/v3.2.0/tools/public_data_updater.py#L247)、[技能更新器](https://github.com/Noneoi/KQPetInventoryExtension/blob/v3.2.0/tools/public_skill_updater.py#L59)、[活动更新器](https://github.com/Noneoi/KQPetInventoryExtension/blob/v3.2.0/tools/public_activity_exchange_updater.py#L1336)、[更新服务](https://github.com/Noneoi/KQPetInventoryExtension/blob/v3.2.0/src/application/runtime/data_update_service.cpp#L185)。这些结论来自静态代码，不等同于已经在正式包复现全部用户症状。

v3.2.0 已有点击后立即显示忙碌、任务互斥、失败保留旧数据、单类更新、活动模块复用等机制。实施应在此基础上补齐请求受理和结果恢复，不能把已有能力重复算作新增功能。

## 三 设置中的数据更新页面

保留一个主要操作“检查并更新全部资料”。下面用六行展示六类资料，各行显示最近检查时间、最近成功应用时间、当前状态和变化摘要。

| 页面内容 | 用户能看到或执行的操作 |
|---|---|
| 当前任务 | 正在获取、反编译、解析、检查或保存；已用时间；完成数量；复用数量 |
| 六类结果 | 已更新、无变化、部分完成、失败保旧、未检查，状态与原因分开显示 |
| 失败恢复 | 只重试未完成项，必要的关联项会说明原因后一起处理 |
| 取消 | 在安全阶段停止；正在提交时等待当前提交完成，不把半成品当成现用资料 |
| 查看变化 | 新增精灵、技能或商品，价格、次数与有效期变化；待识别活动单列 |
| 高级操作 | 单类更新、完整重新核验、查看来源与导出诊断 |
| 重开窗口或重启 | 恢复上次持久结果；中断任务明确标为未完成，不恢复成成功 |

任务使用唯一身份，界面“点击已受理”和后台“已开始”分别反馈。重复点击合并到当前任务；被补图、缓存管理或另一个更新任务占用时显示具体阻塞原因，旧任务的回调不能覆盖新任务状态。

同一页面保持软件版本更新与游戏资料更新的区别。数据更新完成不能冒称账号余额、兑换次数或任务进度也已刷新。

主要改动位置：标签版本中的 `pet_settings_dialog.cpp/.h`、`data_update_service.cpp/.h`、`application_runtime.cpp`。状态展示从结构化任务记录生成，避免靠拼接一段错误文字表达全部结果。

## 四 六类数据更新的内部改良

### 准确识别官方变化

统一处理 Flash 与 H5 的版本、文件映射和覆盖规则，以已有核实的官方加载方式为依据。H5 的资源别名、压缩配置路径和 `start.files` 覆盖要进入依赖身份；Flash 的入口版本、版本表和临时覆盖分别留存。

正常更新先发现当前依赖，再判断哪些内容变化。对关键版本表、目录和直接消费配置核对实际来源内容；来源不明确时不能只凭版本字符串显示“已是最新”。完整重新核验可重新获取当前实际依赖并核对字节，但相同字节仍可复用有效反编译结果。

规则变化应触发受影响任务重新解析。同版本官方修订、仅覆盖项变化、局部规则修正、临时版本表不可用等情况都需要独立测试。网络失败和官方新结构分别记录，不能都归为“没有更新”。

### 提取与解析缓存

建立三层记录：本次核验的官方资源、从资源导出的脚本或配置、业务解析结果。三层分别绑定实际来源和影响结果的规则，避免只改活动解释就让所有精灵资料重新反编译。

相同 SWF、相同导出工具和相同导出范围的结果可以跨次复用。一个文件需要多个类时合并提取，先验证合并导出与单独导出等价。缓存需检查实际内容、路径、清单和容量；损坏或不匹配的条目拒绝复用。

独立网络获取可在共享去重后做有限并发；耗内存的 Java 提取先测试 1 至 2 个工作进程。各任务使用独立输出和固定输入，结果由协调器合并。不能直接把当前六个方法放进线程池共享可变状态。

### 候选检查与应用

下载和解析先写候选目录，检查基本结构、字段类型、必要表、精灵关联、商品身份及来源记录，再应用到现用资料。后续已验证的字段映射和原文核对修复按实际需要移植，未知字段变化保持明确提示。

消费者使用同一次已发布快照。精灵定义与依赖它的技能或商品关联需要一致时一起切换；图片失败不应阻止已检查通过且与之独立的文本资料。未选择的类别沿用原引用，避免把全部六类无条件绑定为同成同败。

保留上一份有效资料和应用记录，区分检查通过、文件提交成功、当前工作台载入成功。磁盘成功但载入失败时提供“重新载入已保存资料”，不要求再下载一遍。

实现过程中保留既有账号详情、勾选记录、材料观察和个人配置。公共资料更新不能重置用户取消的默认商品，也不能给新手动商品继承旧的整店勾选。

### 完整的活动发现

继续从官方目录、HUD、近期发布及实际关联入口发现活动，处理公共奖励、礼包、进化选择器和有效期面板。缓存没有相关奖励的结果也需要绑定来源与规则，新增内容不能被旧负结果永久屏蔽。

活动改名、换日期、换奖励、调整费用与限次按结构处理；新结构记录具体未识别位置。保留 v3.2.0 已明确排除的活动和自选范围，完整扫描不等于恢复用户已经要求排除的内容。

## 五 其他功能的优化安排

| 优先级 | 功能 | 已有能力与改良重点 | 完成标准 |
|---|---|---|---|
| P1 | 商店与手动补充 | 已有取消默认项目、批量操作、过期隐藏和未识别说明。增加统一状态查看：当前可用、未开始、已结束、手动隐藏、待识别；分开显示目录时间与余额、次数观察时间 | 用户能查明商品为何没出现；更新不丢选择；未知价格或次数不显示成已足够 |
| P1 | 精灵详情刷新 | 已有暂停、继续、进度和失败重试参数。增加本轮失败清单及“只重试失败/缺失项”，对连续超时做受限退避，明确离线等待 | 不重读已完成项；队列可恢复；换账号不串入上个账号的返回；不靠加大发包并发提速 |
| P1 | 资产与养成分析 | 已有分片工作、派生缓存和旧结果保留，正式版说明仍有万级个体预算限制。优先减少重复装载和商品匹配，研究固定快照下分批继续与变化实例增量重算 | 达到预算时说明已完成和未完成范围；保留可继续的工作；局部结果不冒充全账号统计 |
| P2 | 日常状态 | 已有手动刷新和账号进度缓存。强化公共活动目录与账号进度的分别更新时间、失败保留和周期状态 | 更新目录不把账号进度标成最新；旧周期或未知次数有明确标记 |
| P2 | 图片与缓存管理 | 已有按需补图、失败重试、备份、恢复和目录迁移。增加失败图片定向补齐及分类空间说明，区分账号原始数据、公共资料、工具和可重建缓存 | 清理影响可判断；避免删图或删派生缓存导致账号详情丢失；正常查看继续复用图片 |
| P2 | 诊断与操作反馈 | 把数据更新、详情队列、分析和补图的失败阶段分别记录；面向用户显示可执行的恢复动作 | 能区分网络、资源变化、解析、磁盘、排队和载入问题，无需连续多次点按钮试探 |

资产的容量问题有发布说明和 `analysis_worker.cpp` 的预算分支依据；其他项目主要是现有能力上的体验与恢复改良，不把它们一概宣称为已复现故障。保留现有手动刷新边界，不新增后台账号轮询。

## 六 实施批次

| 批次 | 工作 | 交付条件 |
|---|---|---|
| A 基线与正确性 | 固定 v3.2.0 来源，准备隔离数据样本；复现版本识别和连续点击场景；补齐 Flash、H5 加载链与失效规则；加入分步骤计时 | 能证明同版本覆盖变化、规则变化和失败恢复处理正确；建立该正式版自己的性能基线 |
| B 更新体验与应用 | 六类结果面板、任务身份、取消、失败定向重试、候选检查、依赖一致应用、载入确认与上一版恢复 | 一次点击有明确受理结果，重开设置能看到真实状态；没有关联资料混用或把部分成功写成全部成功 |
| C 提速与商店体验 | 持久提取缓存、同源合并、按变化解析、必要的有限并发；商店隐藏原因与数据时间 | 无变化和小变化更新的同输入配对测量有改善；完整活动发现和用户勾选不退化 |
| D 其他功能 | 失败详情补读、大账号分析分批与增量、日常与缓存状态改良 | 各功能单独回归，通过后再合入；不将所有页面重做绑到数据更新发布上 |

建议第一轮先完成 A、B，再交付 C。D 按影响与实际使用量逐项推进。目标是先让更新正确、结果清楚，再以测量决定性能改动；不预先保证固定秒数。

## 七 验收与版本迁移

必须覆盖以下场景：

1. 六类分别更新及全部更新，Flash 不可用时不无故阻断只依赖 H5 的检查。
2. `v/lv` 不同、覆盖映射改变、同版本文件变化、解析规则改变和新资源出现。
3. 官方无变化连续检查、小规模活动变化和较大资料更新，分别记录下载、反编译、解析、检查、保存和载入耗时。
4. 连续点击、关闭再开设置、用户取消、断网、磁盘失败和提交前后中断。
5. 新活动、深层关联入口、活动下架、期限改变、负缓存失效和未识别结构保留。
6. 商品选择、账号详情、材料余额、兑换次数与历史记录保持；公共更新不伪造账号状态刷新。
7. 一千、五千、万级个体样本中的详情刷新和分析容量，记录完整进程内存与实际完成范围。

性能测试在隔离目录固定来源和工具，做至少五组同输入配对；联网体验单列。重用 v3.2.0 的测试并为新增行为补回归，发布说明中的既有测试通过记录不代替新产物验证。

从 v3.2.0 源码开发不等于把正在使用的客户端直接降级。交付时分别验证：仍使用 v3.2.0 的 `catalog/` 资料，以及本机后续版本已经形成的 `public/` 资料清单。需要迁移的六类按实际格式导入候选，不读取旧目录后误报已使用最新资料；旧程序与资料保留可回退入口。

最终版本号按发布渠道和已安装版本确定，生成新的正式发布，不改写 `v3.2.0` 标签或替换原发布资产。继续使用现有配对构建、测试报告绑定、打包和部署流程。

本次交付为方案和基线记录，当前源码实现及日常客户端保持原状。
